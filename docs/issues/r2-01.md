## Результат

Усі ролі мають одну структуру даних, working API skeleton та synthetic report, на якому можуть почати інтеграцію.

## Код і файли

services/api/pyproject.toml; services/api/src/vic/contracts.py; main.py; api/; contracts/openapi.json; contracts/fixtures/*.json; README.md

Це очікувані шляхи реалізації; на момент планування код ще не створено. Використовуємо один package `vic`, contracts і LLM adapter R2.

## Що за чим робити

1. Створити встановлюваний Python package vic, FastAPI app і GET /health; записати install/start commands.
2. Реалізувати models, enums, 11 section keys і error envelope зі спільної специфікації; узгодити поля з R1/R3/R4/R5.
3. Створити synthetic case/evidence-pack/report-v1/report-v2 і running/failed fixtures. R3 перевіряє provenance, R4/R5 — предметний зміст.
4. Додати case/run/report routes спочатку з явно позначеними mock handlers; export OpenAPI.
5. Передати R1 API приклади, всім backend-ролям imports/signatures і RunContext interface.

## Критерії готовності

- [ ] Документована команда запускає GET /health.
- [ ] Усі fixtures проходять Pydantic validation та ID checks; report містить 11 sections і 5–10 questions.
- [ ] Invalid input повертає 422 error envelope, unknown case — 404.
- [ ] Contract changes і mocks явно описані; інші ролі можуть імпортувати models.

## Як перевірити

Запустити API, надіслати валідний/порожній CaseInput, перевірити responses; валідатор читає кожен fixture.

## Що передати команді

R1 отримує OpenAPI/fixtures; R3/R4/R5 отримують Python types. Це перша інтеграційна залежність всієї команди.

У PR: посилання на цю задачу, опис working behavior, commands/input/result перевірки та відомі обмеження. Не закривати live-задачу лише на mock output. API/schema change погодити з R2 і споживачами.
