## Результат

Один input проходить API → evidence → agents → audit → chair → validated report із trace й збереженням.

## Код і файли

services/api/src/vic/storage.py; llm.py; run_context.py; pipeline.py; report_builder.py; api/runs.py; tests

Це очікувані шляхи реалізації; на момент планування код ще не створено. Використовуємо один package `vic`, contracts і LLM adapter R2.

## Що за чим робити

1. Реалізувати case/run/snapshot/report repository; report version виділяти atomic.
2. POST run повертає 202; background stages і recovery interrupted runs документовані.
3. Створити structured LLM adapter: schema validation, bounded retries/repair, usage, config versions.
4. Підключити функції R3/R4/R5 у порядку контракту; стubs дозволені тільки у явно synthetic development mode.
5. Після chair перевірити нові claims і completeness; критичні audit findings не ігнорувати.
6. Додати timeout/budget/provider/source failures; approximate cost unavailable не означає 0.
7. Надати R1 production start/health/storage/auth/env requirements.

## Критерії готовності

- [ ] Working run з реальними model calls створює збережений Report.
- [ ] Stage/status змінюються; failed/restarted run не висить назавжди running.
- [ ] Invalid output або критична unresolved factual помилка не стає завершеним впевненим рішенням.
- [ ] Trace містить model/prompt/config/snapshot/usage/latency; secrets відсутні.
- [ ] Повний live pipeline перевірено після підключення залежних modules.

## Як перевірити

Пройти HTTP happy path; симулювати timeout/invalid JSON/source outage; restart і прочитати report; final output має 11 sections.

## Що передати команді

R1 підключає polling; R4/R5 використовують adapter; R3 підключає retrieval/audit.

У PR: посилання на цю задачу, опис working behavior, commands/input/result перевірки та відомі обмеження. Не закривати live-задачу лише на mock output. API/schema change погодити з R2 і споживачами.
