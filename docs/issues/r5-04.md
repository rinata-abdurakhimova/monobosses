## Результат

Є чесний звіт про фактичну якість, leakage controls і defects, а не лише красивий demo report.

## Код і файли

evals/rubric.md; evals/cases/ manifests; evals/error-log.md; docs/evaluation-report.md

Це очікувані шляхи реалізації; на момент планування код ще не створено. Використовуємо один package `vic`, contracts і LLM adapter R2.

## Що за чим робити

1. Зафіксувати rubric і release gates до holdout runs; критичні defects окремо від середнього score.
2. Synthetic старт, за ресурсами 12–20 cases різних indications/mechanisms/stages.
3. Manifest: family/input/pack/type/as-of/expectations/allowed decisions/leakage/split; labels не у runtime input.
4. Розділити dev/holdout за family; anonymous/temporal лише за перевірених controls R3.
5. Runner R2 → per-case reports; manual review R3/R4/R5; LLM judge тільки допоміжно.
6. Порахувати exact denominators, critical omissions/unsupported claims, decision rationale, revision behavior, runtime/cost.
7. Error log з owners/fixes; повторити affected dev checks; frozen holdout config; описати limitations.

## Критерії готовності

- [ ] Маніфести/splits/expectations відтворювані; пов’язані paired variants у одному split.
- [ ] Результати по кейсах і denominators доступні.
- [ ] Leakage flags і невизначені controls явно описані.
- [ ] Немає твердження про expert Unobio agreement без їх labels.
- [ ] Критичні release defects усунені або явно блокують release.

## Як перевірити

Запустити documented runner; вручну перевірити major claims/critical red flags; перевірити holdout не використано для tuning.

## Що передати команді

TEAM-01 використовує evaluation report/gates; R1/R2 отримують фактичні runtime/cost limits.

У PR: посилання на цю задачу, опис working behavior, commands/input/result перевірки та відомі обмеження. Не закривати live-задачу лише на mock output. API/schema change погодити з R2 і споживачами.
