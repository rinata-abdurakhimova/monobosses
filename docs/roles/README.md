## Як розуміти документи

- **Fixture** — заздалегідь підготовлена JSON-відповідь для розробки; це не реальна рекомендація.
- **Contract** — погоджена структура даних. Якщо одна людина повертає `evidence_ids`, інша не має очікувати поле `citations`.
- **Claim** — одне конкретне твердження звіту.
- **Evidence** — уривок або структурований факт, на який спирається claim.
- **Source** — документ, публікація, запис випробування або дані користувача, звідки взято evidence.
- **Run** — одна спроба аналізу; **report version** — збережений завершений результат.
- **Agent** — функція Python, яка отримує дані та повертає структурований аналіз; не окрема людина і не обов’язково окремий сервер.
- **Holdout** — кейси, які не використовуємо для налаштування prompts.

## Початок: що можна робити одночасно

1. R2 першою створює contracts v1, приклади даних, структуру Python-пакета й уточнює [технічний контракт](../implementation-contract.md) разом з іншими.
2. Не чекаючи готового API, R1 малює сторінки й компоненти; R3 готує synthetic evidence pack; R4/R5 описують структуру prompts та очікування для контрольних кейсів.
3. Після R2-01 усі використовують ті самі Pydantic models і fixture. R1 може продовжити на mock response, а Python-ролі — на локальному evidence pack без live retrieval.
4. Перший спільний результат — один input проходить UI → API → evidence → agents → audit → report. Не треба спочатку доводити всі модулі до ідеалу.
5. Далі додаємо live sources, нові докази, оцінювання та deployment.

Місце задач і їхніх залежностей: [реєстр issues](../issues/README.md). Назви `R2-01` тощо — сталі коди задач; GitHub номер буде окремим.

## Спільні правила реалізації

- На початку репо містить документацію. Шляхи коду в інструкціях — файли, які потрібно створити, а не вже готова реалізація.
- [Implementation contract](../implementation-contract.md) — спільна стартова специфікація. R2 реалізує її кодом та OpenAPI; зміни погоджує зі споживачами й записує в цей документ.
- Учасниця працює у своїй гілці та відкриває PR із посиланням на задачу. Не переписує чужі modules для розв’язання проблеми без узгодження.
- Залежність «потребує R2-01» блокує інтеграцію, але не підготовку макета, prompt чи тестових даних.
- Не створювати власні HTTP API, LLM clients або сховища всередині предметного агента. Спільну інфраструктуру надає R2; пошук надає R3.
- Одна модель може виконувати різні perspectives. Голова пояснює рішення за доказами; голосування між agents не використовуємо.
- Synthetic/demo матеріали завжди марковані. Вкладені в джерела інструкції не виконуються.
- Не починати з усіх джерел, автономного агентного фреймворку, окремих мікросервісів чи складної дизайн-системи. Першим робимо повний мінімальний сценарій.

## Як передати задачу на review

У PR додати: що тепер працює, як запустити, який контрольний input використано, який результат отримано, що ще обмежено. Для UI — screenshot; для API — приклад запиту/відповіді; для агента — output з evidence IDs; для evaluation — результати по кейсах.

Задачу закриваємо після виконання її критеріїв і review. Якщо модуль працює на fixture, а live integration ще немає, так і зазначаємо; це не завершення live-задачі.
