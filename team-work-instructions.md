Конкретні технічні рішення, етапи й пороги перевірки нижче — пропозиції цього плану, а не цитовані вимоги організаторів. При конфлікті пріоритет має поточна вказівка користувача.

## 2. Що маємо отримати

Користувач вводить indication + mechanism/target, додає доступні дані та отримує звіт із рекомендацією, аргументами, невідомостями й джерелами. Для indication + mechanism оцінюємо **підхід**; конкретну **програму** оцінюємо лише за наявності її даних. Об’єкт оцінки завжди видно у звіті.

Мінімальний завершений продукт:

- Робочий вебінтерфейс з усіма 11 пунктами Investment Underwriting Report.
- Перехід **Recommendation → Claims → Evidence → Sources**, включно з фрагментом, що підтримує твердження.
- Наукові, клінічні та комерційні перспективи, аудит доказів і пояснене рішення голови.
- Додавання нового документа або текстового доказу з новою версією звіту й поясненням змін.
- Щонайменше дві різні комбінації indication × mechanism; обробка невідомого запиту через той самий pipeline.
- Відтворювані запуск, traces, версії моделей і prompts, приблизна вартість одного аналізу та результати оцінювання.

IP, партнерства й пороги привабливості розвиваємо після основного сценарію. Критичні ризики, невідомості та 5–10 diligence questions входять у MVP, навіть якщо окремого агента-опонента ще немає.

## 3. П’ять людських ролей

Людська роль — зона відповідальності розробника. AI-роль — аналітична перспектива продукту. Один розробник може реалізувати кілька AI-перспектив; вони не потребують п’яти окремих сервісів чи окремої LLM на кожну перспективу.

| № | Людська роль | Основна зона | Виконавець |
| --- | --- | --- | --- |
| R1 | Product UI, frontend, інтеграція та deploy | Дизайн, Next.js, користувацький сценарій, підключення API, реліз | Rinata |
| R2 | Backend platform та agent orchestration | Python API, контракти, збереження, виконання flow, traces | Kateryna |
| R3 | Data та evidence engineering | Retrieval, нормалізація, provenance, аудит доказів | Victoria |
| R4 | Scientific, translational та clinical agents | Біологія, перенесення на людину, клініка й регуляторний контекст | Arina |
| R5 | Commercial, investment та evaluation | Ринок, фінанси, синтез рішення, ризики, методика оцінювання | Uliana |

Розподіл об’єднує суміжні задачі. R1 має весь видимий продукт і тому не отримує власних backend-агентів. R2 будує спільну платформу для трьох предметних напрямів. R3 централізує джерела й перевірки, щоб кожен агент не створював власний retrieval. R4 відповідає за зв’язний ланцюг від біології до клініки. R5 переводить його в інвестиційне рішення та координує перевірку якості.

### R1. Product UI, frontend, інтеграція та deploy

**Відповідає за:**

- Простий дизайн без окремого дизайнера: компоненти, читабельна типографіка, адаптивність і зрозумілі стани.
- Форму indication + mechanism, необов’язкові поля програми, завантаження доказу.
- Стан запуску: етапи, помилки, частковий результат, повторний запит.
- Рекомендацію, картки AI-ролей, 11 секцій звіту, перегляд джерел і «Що перевірити далі?».
- Порівняння версій: попередня й нова рекомендації, змінені твердження, нові докази, rationale.
- TypeScript-клієнт за погодженим API, frontend mocks, інтеграційний сценарій.
- Деплой Next.js і Python-сервісу, конфігурацію доменів, HTTPS, frontend/backend зв’язок та перевірку релізу.

**Отримує:** OpenAPI, приклади відповідей і mock report від R2; структуру джерел від R3; тексти секцій від R4/R5. R2 надає готовий спосіб запуску Python, healthcheck і список env-змінних; R1 не має самостійно ремонтувати backend packaging.

**Готово, коли:** на розгорнутому продукті можна пройти input → report → source → new evidence → revised report; усі стани доступні без відкриття консолі. Мінімальна перевірка — цей наскрізний сценарій і ручна перевірка читабельності та помилок.

### R2. Backend platform та agent orchestration

**Відповідає за:**

- Python API; рекомендована база — FastAPI + Pydantic/OpenAPI.
- Єдині контракти запиту, evidence, висновку ролі, звіту, помилки й прогресу.
- Збереження кейсів, запусків, незмінних версій звітів, evidence snapshots і зв’язку між ними.
- Оркестрацію етапів, обмежені retries, timeout, бюджет викликів, обробку відмов джерел/моделі.
- Адаптер LLM; версіонування prompts, model identifier і параметрів запуску.
- Runtime для аудиту, синтезу та перегляду після нового доказу; валідацію структурованого output.
- Traces, тривалість, token usage і приблизну вартість; backend start/build, healthcheck, `.env.example`.

**Межа:** R2 реалізує виконання голови й аудитора; предметну логіку голови пише R5, критерії аудиту — R3. Предметні prompts R4/R5 не дублюються в оркестраторі.

**Готово, коли:** один кейс проходить увесь flow через API, має `run_id`, відтворюваний snapshot, структурований report і нову версію після доказу. Перевірки охоплюють контракти, timeout/retry, збереження версій та блокування некоректного output.

### R3. Data та evidence engineering

**Відповідає за:**

- Розпізнавання indication/target, синонімів і, де доступно, стабільних disease/target IDs.
- Спільний retrieval: початково PubMed/PMC, ClinicalTrials.gov, Open Targets; підтримку імпорту наданого evidence pack.
- Додаткові джерела за потребою: FDA/EMA, епідеміологія, SEC/компанії та ціни, а не всі конектори одразу.
- Нормалізацію джерел, deduplication, кеш, дати, версії, уривки й точне місце в документі.
- Пошук як підтримувальних, так і суперечливих доказів; облік неуспішних пошуків.
- Аудит `claim → evidence → source`: доступність, відповідність уривка, релевантність популяції/кандидата, незалежність доказів.
- Маркування препринтів, company disclosures і доказів користувача; розмежування факту й AI inference.
- Технічну підготовку evaluation packs, часові обмеження retrieval та перевірку деідентифікації разом із R5.

**Межа:** R3 перевіряє підтримку тверджень, R4/R5 — їх предметну коректність. Наявність URL або цитати сама по собі не підтверджує claim.

**Готово, коли:** ключове твердження можна відкрити до точного уривка; одна публікація в різних переказах не рахується кількома незалежними доказами; непідтверджений claim явно позначений і не стає фактом у фінальному звіті.

### R4. Scientific, translational та clinical agents

**Відповідає за три AI-перспективи:** наукову, перенесення результатів на людину та клінічну розробку.

- Scientific thesis: genetics, expression, disease tissue, pathways, perturbation, animal models, попередні програми; causal evidence окремо від correlation.
- Human translation: molecular effect → human exposure → target engagement → biological response → patient benefit; PK/PD, tissue penetration, safety, therapeutic window, biomarker gaps.
- Clinical plan: популяція, endpoint, comparator, biomarker strategy, обґрунтування приблизного trial size, етапи, аналоги успіхів/невдач і регуляторний контекст.
- Перегляд власних висновків після нового або суперечливого доказу.
- Спільний перелік клінічних фактів для R5: standard of care, unmet need, потрібна користь і можливий наступний milestone.
- Предметні очікування для тестів і перевірку помилок у наукових/клінічних секціях.

**Готово, коли:** кожна перспектива повертає структуровані claims, аргументи за/проти, ризики, невідомості та умови зміни позиції; відсутня ланка translation не замінюється вигаданим результатом. Невдача одного кандидата не автоматично переноситься на весь механізм.

### R5. Commercial, investment та evaluation

**Відповідає за:**

- Market/access: конкуренти, alternative mechanisms, discontinued programs, addressable patients, цінові аналоги й потрібна диференціація.
- Investment: capital/time до milestone, value inflection points, подальше фінансування, сценарії licensing/acquisition/development.
- Прозорі припущення, одиниці, географію, дату й діапазони; розрахунки в Python за явними inputs, якщо є числова основа.
- Логіку голови: вирішальні аргументи, Invest / Conditional / Do Not Invest, умови рішення, пояснення розбіжностей; жодного голосування більшістю.
- Узагальнення risks, critical unknowns і 5–10 пріоритетних diligence questions із впливом відповідей на рішення.
- Специфікацію evaluation: рубрику, набори, очікувані висновки, аналіз помилок і підсумковий звіт.

**Підтримка:** R3 готує snapshots і leakage checks; R4 перевіряє предметні очікування; R2 реалізує evaluation runner і trace export. R5 координує якість, але не виконує всі перевірки самостійно.

**Готово, коли:** рішення узгоджене з аудитом і предметними секціями; числові оцінки можна перевірити; недостатність даних веде до поясненої прогалини, а не до вигаданої ціни/бюджету. Evaluation запускається повторно й показує конкретні помилки, а не тільки середній score.

## 5. Технічні межі та спільні контракти

Рекомендована структура майбутньої реалізації; ці каталоги ще не означають наявного коду:

```text
apps/web/                         # R1: Next.js
services/api/                     # R2: FastAPI, API та orchestration
services/api/src/vic/evidence/        # R3: retrieval, normalization, audit
services/api/src/vic/agents/science/  # R4: science, translation, clinical
services/api/src/vic/agents/business/ # R5: market, investment, chair, risks
contracts/                       # R2: schema, OpenAPI, fixtures
evals/                           # R5: rubric/cases; runner R2; packs R3/R4
docs/                            # architecture, source registry, demo
```

### Контракт до початку незалежної реалізації

R2 збирає коротке погодження з усіма ролями та фіксує:

| Сутність | Мінімальні поля |
| --- | --- |
| `CaseInput` | indication, mechanism/target, optional program data, evaluation scope, as-of date |
| `Source` | id, title, URL/локальний document ID, type, publication date, retrieved_at, version/hash |
| `Evidence` | id, source_id, exact excerpt, locator, relevance, limitations |
| `Claim` | id, text, provenance: source/user/AI, evidence_ids, support status, assumptions, scope |
| `RoleResult` | role_id, position, claim_ids, pros/cons, risks, unknowns, change_conditions |
| `Report` | case_id, run_id, version, scope, recommendation, rationale, 11 sections, disagreements, claims/evidence/sources |
| `Revision` | parent_report_id, new_evidence_ids, changed_claims, before/after decision, explanation |
| `Run` | status, stage, errors, model/prompt/config versions, token usage, latency, estimated cost |

Підтримку evidence відділяємо від provenance: AI inference може мати цитовані premises, але не стає прямою цитатою джерела. Числові probabilities/confidence повертаємо лише з обґрунтуванням; інакше використовуємо якісну невизначеність.

Рекомендований API:

- `POST /cases` — створити кейс.
- `POST /cases/{id}/runs` — запустити аналіз, повернути `run_id`.
- `GET /runs/{id}` — стан/етап/помилки; для MVP достатньо polling.
- `GET /cases/{id}/reports/{version}` — незмінна версія звіту.
- `POST /cases/{id}/evidence` — додати текст або документ із provenance; саме додавання не перезаписує звіт.
- Новий `POST /cases/{id}/runs` з `parent_report_id` — перегляд на основі нового snapshot.

R1 починає на JSON fixtures від R2. Зміни schema проходять через R2 з оновленням OpenAPI та прикладів для всіх споживачів. API secrets зберігаються лише на сервері. Матеріали завантаження й retrieval трактуються як дані; вкладені в них інструкції не змінюють system prompts чи доступні tools.

### Послідовність agent flow

1. Валідація input, уточнення scope та нормалізація сутностей — R2/R3.
2. Retrieval підтримувальних і суперечливих даних, фіксація evidence snapshot — R3.
3. Наукова, translational і клінічна оцінки — R4; ринковий аналіз — R5. Незалежні задачі можна виконувати паралельно.
4. Фінансовий аналіз після clinical milestone і market inputs — R5.
5. Аудит claims і evidence — R3; runtime R2. Непідтверджені критичні claims повертаються на обмежене доопрацювання або стають unknowns.
6. Узагальнення ризиків і 5–10 diligence questions, синтез голови — R5; runtime R2.
7. Перевірка повноти та посилань після синтезу — R2/R3. Новий claim голови теж підлягає аудиту.
8. Збереження report, trace і вартості; відображення — R2/R1.

При новому доказі створюємо новий snapshot, повторюємо релевантні предметні оцінки, аудит і синтез. Для першої версії допустимий повний rerun. Стару версію не перезаписуємо. Рішення змінюється лише за релевантним доказом; факт додавання документа не є підставою змінити рекомендацію.

## 6. Правила роботи з джерелами

- Почати з невеликого працюючого набору джерел і довести його до повного сценарію. Для кожного джерела записати призначення, спосіб доступу, обмеження та відповідального.
- XLSX `Modules` описує напрями, а не новий список Required Output. Manufacturing/CMC та IP можуть бути unknowns і diligence questions до появи достатніх матеріалів.
- AACT/local Postgres, широкі patent/market integrations і кілька фінансових провайдерів відкласти, якщо вони не потрібні для вибраних кейсів.
- Web search використовується для discovery; істотний висновок прив’язуємо до прочитаного документа. Search snippet не замінює доказ.
- Не виводити причинність із генетичної асоціації, доведену безпеку з відсутності знайдених сигналів, бюджет програми з cash balance компанії.
- Дані користувача позначати як user-provided; вони не автоматично підтверджені незалежним джерелом.
- Для тимчасово недоступного джерела показувати прогалину або позначений snapshot. Не видавати кешоване демо за live analysis.
- У `emerging_drug_list.xlsx` є примітка про investigational status станом на 3 жовтня 2026 та потребу перевірки перед використанням. `Depth` — категорія списку, не рейтинг якості чи доказ відсутності leakage. Поточні статуси перевіряє R3 перед вибором кейсу.

## 7. Перевірка якості та контроль data leakage

### Що можемо перевірити зараз

Якість underwriting оцінюємо за коректністю доказів, виявленням ризиків, повнотою й послідовністю рішення. Відповідність експертному висновку — корисний proxy, але не доказ майбутнього investment return. Згода кількох AI-перспектив не є незалежною валідацією.

### Три групи evaluation cases

1. **Синтетичні контрольовані кейси.** Створити узгоджені evidence packs із відомими missing links, safety issues, конкурентними бар’єрами та змінами доказів. Маркувати synthetic у dataset і UI. Рубрику та очікування перевіряють R4/R5; самогенерація LLM не є ground truth.
2. **Деідентифіковані реальні кейси.** Прибрати назви компанії/активу, trial IDs, DOI/URL та інші прямі ідентифікатори; перевірити непрямі підказки: унікальні endpoints, числа, таймлайн, modality/target combination. Вилучення підказок не повинно змінювати науковий сенс. Мапу до оригіналу зберігати окремо від model input. R3/R5 проводять blind re-identification attempts і записують guessed identity та підстави. Успішно впізнані кейси не враховувати як захищені від leakage; невдала спроба не доводить неможливість впізнавання.
3. **Часові кейси.** Використовувати конкретну версію моделі з документованим knowledge cutoff і факти, оприлюднені після нього. Дата релізу моделі сама по собі не доводить cutoff. Фіксувати as-of date й доступні тоді версії джерел; виключати пізніші outcomes та оновлені документи, що їх розкривають. Приклад ментора з GPT-3.5 не є підтвердженням cutoff обраної моделі.

Для blind evaluation використовуємо контрольований evidence-only режим без відкритого retrieval і без оригінальних URL у model input; evaluator окремо зберігає provenance. Інакше retrieval може зняти анонімізацію. Окремо перевіряємо live retrieval на реальних named cases та позначаємо його інший рівень контролю leakage. Temporal tests можуть використовувати лише зафіксований корпус, доступний на as-of date.

### Протокол

- Початковий орієнтир — 12–20 кейсів із кількох indication × mechanism, різних стадій і якості даних. Це внутрішня ціль; фактичний розмір і склад зазначаємо в evaluation report.
- Розділити development та закритий holdout за програмою/родиною пов’язаних кейсів. Варіанти одного кейсу не розносити між цими наборами.
- Зберігати input, evidence pack, as-of date, synthetic/anonymized/temporal flags, expected critical claims/risks, допустимі рішення й rationale, очікувану реакцію на новий доказ, версію рубрики.
- Очікування сформувати до перегляду відповіді системи. Внутрішні оцінки позначати team-reviewed; експертними називати лише оцінки відповідних спеціалістів, зокрема Unobio, якщо вони надані.
- Для кожного кейсу фіксувати model/prompt/code versions, snapshot hash, параметри, latency, token usage та приблизний API cost. Фіксовані параметри не гарантують ідентичність LLM-відповідей; для ризикових кейсів виконати повторні runs і виміряти розкид.
- На holdout не підлаштовувати prompts. Після використання holdout для виправлень він перестає бути незалежною фінальною перевіркою.
- LLM judge допустимий як допоміжний скринінг; факти, цитати та критичні помилки перевіряються окремо R3/R4/R5.

### Рубрика та початкові release gates

Пороги нижче — командні критерії готовності прототипу, які погоджуємо до holdout run. Показуємо чисельник/знаменник і результати по кейсах; малий dataset не дозволяє заявляти загальну точність системи.

| Вимір | Як перевіряємо | Початковий критерій |
| --- | --- | --- |
| Повнота | 11 секцій, scope, 5–10 diligence questions | 100% завершених reports; недостатні дані пояснені |
| Простежуваність | Для кожного major claim відомі provenance і support status; source-based claim веде до excerpt | 100%; для inference/unknown є premises або опис прогалини |
| Коректність evidence | Людина перевіряє, чи excerpt підтримує claim у правильному контексті | ≥90% перевірених major claims; 0 непідтверджених критичних фактів, що визначають рішення |
| Ризики | Очікувані критичні red flags у контрольованих cases | 100% критичних red flags; окремо рахувати хибні red flags |
| Фінансові оцінки | Одиниці, assumptions, діапазони й відтворювані розрахунки або чесна прогалина | 0 вигаданих суттєвих inputs |
| Рішення | Допустима рекомендація та вирішальні аргументи за рубрикою | Окремий результат по кейсах; кожну суттєву розбіжність розібрати |
| Нові докази | Paired before/after: релевантні позитивні, негативні й нерелевантні дані | Коректна зміна на вирішальному доказі; відсутність штучної зміни на нерелевантному |
| Leakage | Прапорці контролю, re-identification та temporal checks | Жодного кейсу з відомим порушенням у leakage-controlled результаті |

Неправильне критичне посилання або пропущений safety risk не компенсуються високим середнім score. R5 веде error log: case → дефект → причина → власник → виправлення → повторна перевірка.

## 8. Порядок командної роботи

Календар визначає команда. Етапи прив’язані до результату, а не до вигаданого дедлайну.

| Етап | Робота | Умова переходу |
| --- | --- | --- |
| A. Scope та contracts | Усі погоджують MVP; R2 schema/fixtures; R3 source plan; R4/R5 rubric; R1 wireframe | Погоджені input/output, 11 секцій, mock report і межі ролей |
| B. Наскрізний каркас | R1 працює на mocks; R2 запускає API/flow; R3 імпорт evidence pack; R4/R5 структуровані outputs | Один кейс проходить через UI й API з реальним model call; fixtures позначені |
| C. Доказовий аналіз | R3 конектори й аудит; R4/R5 предметна логіка; R2 traces/budget; R1 evidence drill-down | Major claims простежуються; другий indication × mechanism працює тим самим flow |
| D. Оновлення та evaluation | R2 revisions; R1 comparison UI; R3/R4/R5 paired cases і leakage checks | Вирішальний новий доказ змінює висновок; є evaluation report і error log |
| E. Release та demo | R1 deploy; R2 backend readiness; всі перевіряють нові запити й документацію | Release gates виконані, наскрізний сценарій працює на deployment |

### Щоденні правила

1. Для задачі визначити owner, результат, залежності й критерій готовності. Один owner відповідає за завершення, інші допомагають за потребою.
2. На початку робочого циклу кожен повідомляє: готовий результат, наступний результат, blocker. Зміни API/source schema оголошуються до інтеграції.
3. Працювати короткими гілками `codex/<topic>` або за погодженою конвенцією команди; PR містить зміну поведінки та проведену перевірку. Номер ролі не означає branch name.
4. Межі каталогів визначають основного власника; спільні файли змінювати з погодженням власника, без паралельних несумісних edits.
5. R2 переглядає API/runtime зміни; R3 — provenance/retrieval; R4 — science/clinical; R5 — business/evaluation; R1 — UI/release. Суттєвий prompt чи schema change потребує повторної перевірки відповідних cases.
6. Інтегрувати малими частинами від етапу B. R1 не чекає готовності всіх агентів, backend не відкладає контракт до кінця.
7. Документувати модель/API usage, джерела й вартість одночасно з реалізацією. Secrets і непублічні дані не комітити; у traces зберігати лише потрібні дані.

## 9. Фінальне демо та незнайомі запити Unobio

Демо складається з двох різних комбінацій indication × mechanism і одного контрольованого переходу висновку. Вибираємо кейси за наявністю перевірних доказів і різним профілем ризиків; назви зі списку emerging drugs самі по собі не є гарантією придатності.

Сценарій обов’язкової зміни:

1. Показати початковий report, його snapshot і причину рекомендації.
2. Відкрити вирішальний claim та evidence, що його підтримує або залишає невідомим.
3. Додати перевірений документ або явно позначений synthetic evidence, який змінює вирішальну передумову.
4. Створити новий run; показати перегляд релевантних ролей, аудит і **фактичну зміну висновку** з поясненням. Для наочності обрати приклад зі зміною категорії рекомендації, а не лише тексту.
5. Показати before/after, збережені суперечності й ризики, які новий доказ не усунув.

Для невідомих запитів Unobio:

- Жодних hardcoded рекомендацій за назвою препарату; однаковий pipeline для підготовленого й нового input.
- Уміти працювати лише з indication + mechanism, уточнювати неоднозначну мішень і явно обмежувати scope.
- Перевірити holdout запити поза двома demo cases, missing data, conflicting evidence та відмову джерела.
- Не стверджувати експертну відповідність до отримання реальних оцінок Unobio. Порівнювати також rationale, ризики й diligence questions, а не лише категорію рішення.
- Мати snapshots для відтворення та резервний демонстраційний запуск із явним маркуванням; вони не підміняють live run під час перевірки нового запиту.

## 10. Definition of Done для команди

- [ ] П’ять людських ролей призначено командою; R1 відповідає за дизайн, frontend, інтеграцію й deploy.
- [ ] Розгорнутий Next.js + Python продукт проходить повний користувацький сценарій.
- [ ] Усі 11 пунктів звіту присутні; scope, невідомості, припущення та джерела видимі.
- [ ] Major claims мають перевірений шлях до evidence; нові claims синтезу теж перевіряються.
- [ ] Дві різні indication × mechanism та нові holdout inputs працюють через спільний pipeline.
- [ ] Новий релевантний доказ змінює висновок у демо; нерелевантний доказ не створює штучної зміни.
- [ ] Evaluation report містить склад dataset, рубрику, leakage controls, фактичні результати й обмеження.
- [ ] Критичні дефекти усунуті; відомі некритичні обмеження документовані.
- [ ] README описує запуск, env, architecture, model/API usage, source attribution, approximate cost per run і traces.
- [ ] Версії reports, prompts, моделей та evidence snapshots дозволяють відтворити й пояснити показаний результат.

## 11. Що додати після основного сценарію

| Розширення концепції | Власник | Залежності |
| --- | --- | --- |
| Окремий критичний опонент і глибокий «Що перевірити далі?» | R5 | Risks від R4/R3; runtime R2; UI R1 |
| Поріг інвестиційної привабливості / target product profile | R5 | Clinical benefit/safety від R4; evidence R3 |
| IP та licensing screening | R5 | Patent provenance R3; клінічний/регуляторний контекст R4 |
| Partnership discovery | R5 | Public company/institution sources R3 |
| Додаткові джерела, selective reruns, оптимізація latency/cost | R3/R2 | Evaluation підтверджує збереження якості |

Розширення не мають затримувати evidence drill-down, evaluation, роботу на нових запитах або обов’язкове демо зі зміною висновку.
